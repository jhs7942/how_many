# 메타 서사 — AI Quiz × 몇명이니: 시간 제약 하의 두 프로젝트가 만든 AI 활용 학습 곡선

> SSAFY 재학 중 진행한 두 프로젝트는 **시간 제약**이라는 같은 변수를 다른 방식으로 풀었다. AI Quiz는 4시간 MVP에서 *제약을 역이용해 LLM 동적 생성을 정적 JSON으로 대체*하는 결정으로, 몇명이니는 1개월 앱 출시 압박에서 *단기 속도를 양보하고 자체 AI 워크플로우를 구축*하는 결정으로. 두 프로젝트는 독립적이지 않다 — **AI Quiz에서 잃은 사람을 몇명이니의 Linear 도입으로 끊었다.** 이 두 산출물은 한 사람의 AI 활용 학습 곡선을 보여주는 한 쌍의 데이터 포인트다.

**대상 프로젝트**
- 📁 [`AI Quiz`](../../AI_quiz/ai-quiz/.claude/portfolio-v2.md) — 4시간 MVP, 정적 JSON 기반 AI 시험 대비 퀴즈 플랫폼
- 📁 [`몇명이니`](./portfolio.md) — 1개월 v1.0 출시, 자체 AI 워크플로우 기반 위치 기반 장소 추천 앱

## 세 개의 학습 곡선

### 1. 협업 인프라 — "잃은 사람"에서 "연결된 AI"로

**AI Quiz (학습 발생 지점)**
- 콘텐츠 팀원 2명이 업무 분배 비가시성으로 소외감 → 이탈
- 즉시 대응 실패. **프로젝트 종료 후 회고에서 깨달음**
- 이탈한 팀원이 다른 프로젝트에서 활약하는 모습을 보며 *"내가 사람을 잃게 만들었다"* 체감
- 결론: **"협업 인프라 = 속도의 반대가 아니라 속도의 전제"**

**몇명이니 (학습 적용 지점)**
- 초기 같은 패턴 재발 — 본인 일방 개발 + 팀원에게 설명만 하는 구조
- v1.0 출시 후 v1.1 고도화 시점에 **Linear 도입**으로 의식적으로 끊음
- 단순 도입이 아닌 **메타 결정** — "2인 팀 Linear는 관리비용이 효과를 초과한다"는 통념을 *AI 자동화로 관리비용을 0에 수렴시켜* 회수
- 결과: 본인의 AI ↔ 팀원의 AI가 Linear를 매개로 연결되는 협업 시스템 정착

**곡선의 의미** — 학습이 인지에서 끝나지 않고 *다음 프로젝트의 구조 결정*으로 이어졌다. AI Quiz의 회고 문장("how_many 이후 Linear 도입의 직접 계기")이 실제로 실행된 사례.

### 2. AI 활용 — "도구"에서 "워크플로우"로

**AI Quiz**
- Claude Code 누적 1개월 + Vite·Supabase 첫 사용
- AI는 **"4시간 데드라인을 넘기 위한 가속기"** 로 사용
- *"AI 도구가 숙련도 공백을 메울 수 있다"는 가설에 근거한 도박*
- 산출물: v2 코드, 1,160 문제 콘텐츠

**몇명이니**
- 첫 바이브 코딩 → 자체 dev 파이프라인(`CLAUDE.md`, dev-orchestrator, sub-agent, Google Play MCP, Linear sync) 구축
- AI는 **"개발 라이프사이클 전체에 통합된 워크플로우"** 로 내재화
- 단계적 진화: v1.0까지 1인 자체 플로우 → v1.1부터 Linear 추가 → 팀원의 AI까지 연결
- 산출물: 코드 + plan.md(작업당 100~200줄) + .claude/fix/ 트러블슈팅 + study 노트 + 자동 배포 파이프라인

**곡선의 의미** — *AI 사용량이 증가한 게 아니라 AI가 차지하는 라이프사이클 단계가 확장됐다.* "코드 생성"에서 "기획·구현·배포·협업·문서화"까지. 이 확장이 **단기 속도를 양보하면서도 후반 효율(유지보수·재작업·인수인계)을 회수**하는 트레이드오프 구조를 만듦.

### 3. 측정·기획 의식 — "정립"에서 "후퇴"로 그리고 다시

**AI Quiz** — 측정 의식 정립
- 4축 사전 가설 명시 (속도·비용·가용성·범위 적합도)
- 사후 관찰로 모두 확증
- 가설 미수립 영역(주관식 정답률)이 반증으로 드러남(40.7%) → "측정하지 않은 것은 측정되지 않는다"는 학습

**몇명이니** — 의식 후퇴 (정직 기록)
- 사전 가설 **전무**. 첫 바이브 코딩 + 속도 집착 + Claude Code 자체 학습이 동시 작용한 결과
- 실사용 데이터(다운로드·MAU·결과 저장 건수) 미수집
- 다만 우연히 누적된 산출물(plan.md, fix/, study)이 사후 가치를 드러냄

**곡선의 의미** — 학습이 단조 증가하지 않는다는 정직 기록. AI Quiz에서 정립된 측정 의식이 몇명이니에서는 후퇴 — 학습 도구(Claude Code)가 바뀐 시점에서 측정 의식이 후순위로 밀린 것. **다음 프로젝트의 첫 30분에 측정 지표를 정의**하는 게 두 프로젝트가 함께 만든 명확한 다짐.

## 반복된 패턴

두 프로젝트에 공통으로 나타난 구조 — 긍정·부정 모두.

### 긍정적 반복

- **제약을 좁힘으로 활용** — AI Quiz: "시험 범위 고정"이라는 제약이 LLM 동적 생성을 기각하고 정적 JSON을 강제. 몇명이니: "1개월 + 첫 바이브 코딩"이라는 제약이 자체 플로우를 단계적으로 구축하게 함. *제약이 많을수록 "덜 하는 것"이 승리 전략*.
- **롤백 비용을 낮춘 구조 선택** — AI Quiz: 정적 JSON + Vercel 재배포로 가설 실패 시 빠른 교정. 몇명이니: dev-orchestrator + plan.md로 매 작업의 의사결정이 추적 가능, HM-21 같은 1차 구현 롤백을 정밀하게 수행.
- **외부 피드백 수용** — AI Quiz: 강사 피드백("단순 구현은 포트폴리오에 못 쓴다")으로 포트폴리오 재작성. 몇명이니: HM-21 사용자 기대 미충족으로 1차 구현 롤백 후 재설계.

### 부정적 반복 (남은 한계)

- **사용자 기대 사전 검증 부재** — AI Quiz: 주관식 정답률 가설을 세우지 않은 채 출시 → 반증. 몇명이니: HM-21 1차 구현이 사용자 기대(카톡 Feed 썸네일)와 어긋나 롤백. 두 번 다 *"사용자가 기대하는 것"을 만들기 전에 검증하지 않은 비용*.
- **측정 인프라 후순위** — AI Quiz: 4시간 데드라인에서 측정 인프라는 오버헤드로 판단. 몇명이니: 1개월 출시 압박에서 측정 인프라 부재. 두 번 다 *"빠르게 만들기"가 "재대로 검증하기"를 압도*.
- **프로젝트 레벨 Anti-scope 의식 약함** — AI Quiz는 작업 단위 Anti-scope는 명시적이었으나 결국 "오답노트는 로그인 필요" 같은 잘못된 스코프 조기 좁힘이 있었음. 몇명이니는 작업 단위(HM-21 OUT)는 정밀하나 프로젝트 레벨 Anti-scope 의식 자체가 부재.

## 다음 프로젝트로 이식할 원리 (두 번의 경험에서)

두 프로젝트 회고에서 공통으로 도출된 원리들. 다음 프로젝트의 첫 30분 체크리스트 후보.

1. **첫 30분에 협업 인프라 세팅** — Linear·노션·Slack 무엇이든. *협업 도구는 속도의 반대가 아니라 속도의 전제*. 두 프로젝트가 사람의 비용을 치르고 도달한 결론.

2. **첫 주에 사전 가설·측정 지표 정의** — 측정하지 않는 것은 검증되지 않는다. 가설이 모호해도 *지금 무엇을 모르는가*를 명시하는 것만으로 사후 학습이 가능해짐.

3. **사용자 기대를 1차 구현 전에 검증** — 텍스트·와이어프레임·시나리오라도. HM-21 롤백과 AI Quiz 주관식 반증 둘 다 *기대 검증 부재*가 공통 원인.

4. **제약이 선택을 강제하는 구조를 명시적으로 그리기** — "이 제약이 어떤 선택을 가능하게 하는가"를 종이에 적기. 제약이 많을수록 *덜 하는 것*이 승리 전략.

5. **AI를 도구가 아닌 워크플로우로** — 코드 생성기로 쓰지 말고 라이프사이클 전체에 통합. 단기 속도 ↓이지만 후반 효율(유지보수·재작업·인수인계)로 회수. *팀원의 AI까지 연결되면 협업 시스템으로 확장 가능*.

6. **"통념적 ROI 한계"를 AI 자동화로 회수 가능한지 먼저 확인** — Linear는 2인 팀에서 ROI가 안 나온다는 통념이 있지만, AI 자동화로 관리비용을 0에 수렴시키면 다른 답이 나옴. 다음 프로젝트에서도 *"이 도구의 통념적 한계를 AI 자동화로 어디까지 끌어내릴 수 있는가"* 를 먼저 묻기.

## 메타 회고 — 두 포트폴리오의 재작성 의식

AI Quiz 포트폴리오는 강사의 *"단순 기능 구현은 포트폴리오에 쓸 수 없다"* 피드백 후에 v2로 재작성됐다. 그 학습이 몇명이니 포트폴리오 작성 시점부터 직접 적용됐다 — *"무엇을 만들었는가"가 아니라 "어떤 판단을 어떤 제약 하에 내렸는가"* 를 7단계(Context → Problem → Analyze → Hypothesis → Action → Result → Learnings)로 작성. 이 메타 서사 자체가 두 포트폴리오를 한 학습 곡선으로 묶는 세 번째 산출물이다.

두 프로젝트는 코드 어필이 아니다. **두 번의 시간 제약 + 두 번의 협업 학습 + 두 번의 측정 의식 + 한 번의 워크플로우 내재화** — 이 6개의 데이터 포인트가 한 사람의 의사결정 해상도를 증명하는 자료다.
