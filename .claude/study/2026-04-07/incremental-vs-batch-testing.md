# 점진적 수정 vs 일괄 수정 테스트 전략

## 학습 환경
- 날짜: 2026-04-07
- 관련 프로젝트: how_many (몇명이니)
- 기술·버전: Playwright E2E, Next.js 16

---

## 배경

Playwright E2E 테스트 22개 중 13개가 실패하는 상황에서, 하나씩 수정하고 매번 테스트를 돌리는 점진적 방식으로 진행. 12회 테스트 실행 끝에 해결했지만, 근본 원인(UrlNormalizer)을 7번째 반복에서야 발견. 일괄 수정 방식이었으면 3회 테스트로 끝났을 것.

---

## 핵심 개념

### 점진적 수정 (Fix-one → Test → Repeat)
- 에러 하나 수정 → 테스트 실행 → 결과 확인 → 다음 에러 수정
- 피드백 루프가 짧지만, 사이클 수가 많아짐
- 근본 원인을 모른 채 증상만 치료하면 무한 루프에 빠짐

### 일괄 수정 (Analyze-all → Fix-all → Test)
- 전체 실패를 수집 → 소스 코드까지 읽고 근본 원인 분류 → 한번에 수정 → 테스트
- 초기 분석 시간이 더 걸리지만, 총 사이클 수가 적음
- 근본 원인이 소수일 때 특히 효과적

---

## 실제 적용

### 언제 어떤 방식을 쓸까

| 상황 | 적합한 방식 | 이유 |
|------|------------|------|
| 다수 실패가 소수 근본 원인에서 파생 | 일괄 | 원인 하나 잡으면 여러 실패가 동시 해결 |
| 에러들이 서로 독립적 | 점진적 | 각 수정이 다른 에러에 영향 없음 |
| 코드베이스를 잘 모름 | 점진적 | 테스트 결과가 코드 이해를 도움 |
| 수정 간 충돌 가능성 | 점진적 | 충돌을 조기 발견 |
| 코드베이스를 충분히 이해 | 일괄 | 분석 정확도가 높으므로 한번에 처리 가능 |

### 이번 세션 (점진적, 비효율)
```
12회 테스트 실행, ~80분 소요
증상 치료 → 새 증상 발생 → 되돌리기 반복
workers:1 적용 → 오히려 3개 추가 실패 → 되돌림
UrlNormalizer 발견은 7번째 반복에서
```

### 이상적 접근 (일괄, 추정)
```
1회: 실패 목록 수집
소스 코드 읽기 (10분): UrlNormalizer, session.ts, splash 발견
전체 수정 후 2회: 검증
잔여 이슈 수정 후 3회: 최종 확인
총 ~25분
```

## 주의사항

### 핵심 공식
> **근본 원인 분석에 투자한 시간 ∝ 절약되는 수정-테스트 사이클 수**

증상을 바로 고치고 싶은 유혹이 있지만, 소스 코드를 10분 더 읽는 것이 테스트 40분을 절약한다.

### 판단 기준 체크리스트

수정 전에 스스로 물어볼 것:
1. 이 실패의 **근본 원인**을 알고 있는가? (모르면 소스 코드부터 읽기)
2. 여러 실패가 **같은 원인**에서 나온 것 같은가? (그러면 일괄 수정)
3. 이 수정이 **다른 테스트에 영향**을 줄 수 있는가? (그러면 점진적)
4. 수정 후 결과를 **예측할 수 있는가?** (예측 가능하면 일괄, 불확실하면 점진적)
