# 몇명이니 (how_many) — 첫 바이브 코딩 프로젝트에서 AI를 도구가 아닌 워크플로우로 내재화

> SSAFY 사이드 프로젝트로 시작한 위치 기반 장소 추천 앱. **첫 바이브 코딩**이라는 실력 제약 하에서 단기 개발 속도를 양보하고 자체 AI 워크플로우(Claude Code + Google Play MCP + Linear 자동화)를 구축, **시작 31일 만에 Play Store 출시**(2026-03-16 → 2026-04-16). 1차 출시까지 1인 자체 플로우로 운영, 출시 후 v1.1 고도화부터 Linear 도입으로 협업 본격화. 수동 빌드·배포 30분 → MCP 자동 3분, v1.1 고도화 9일간 Linear 이슈 25건 관리. 코드 어필이 아닌 **"AI를 워크플로우로 내재화한 첫 사례"**로 어필.

**기간** · 2026.03.16 ~ 진행 중 (v1.0 출시 2026.04.16, v1.1 안정화 단계 2026.04.16~)
**역할** · 개발·배포·기획 단독, 기술적 의사결정 단독 / 팀원: 기획·QA 1명
**팀 구성** · 2인 (SSAFY 교육 과정에서 만난 사이드 프로젝트 팀)
**스택** · Next.js 16, TypeScript, Tailwind v4, Supabase (Realtime + DB), Capacitor (Android), Vercel, Linear

## Context

**소속·동기** — SSAFY 정규 과정에서 만난 팀원과 **개별 사이드 프로젝트**. 학원 정규 과제도 외부 발주도 아닌 **학습용**. 본인 동기는 ① AI 협업 워크플로우 체득 ② SSAFY 후 취업 포트폴리오 부재 해소 ③ 첫 앱 출시 경험.

**병행 맥락 — 협업 실패의 학습** — 본 프로젝트 초기 자체 개발 플로우 구축 단계에서 **AI Quiz 프로젝트를 병행**. AI Quiz는 4시간 MVP + 시험 대비 개선이라는 짧은 사이클이라 먼저 종료. 그 과정에서 콘텐츠 팀원 2명이 업무 분배 비가시성으로 소외감을 겪고 이탈하는 경험. 이탈한 팀원이 다른 프로젝트에서 활약하는 모습을 보며 "협업 인프라 부재 = 사람을 잃는 비용"을 체득. 이 학습이 **본 프로젝트 v1.0 출시 후 v1.1 고도화 단계에서 Linear 도입**으로 직접 이어짐.

**시간 제약** — SSAFY 본 과정과 병행. **1개월 만에 v1.0 출시** 강제. 디테일 구성·코드 이해 둘 다 후순위로 밀림.

**실력 제약** — 첫 바이브 코딩 프로젝트. **코드 흐름을 100% 이해하지 못한 채** 진행. 본인이 이를 인지하고 어필 축을 코드가 아닌 **AI 활용 워크플로우**로 의식적으로 전환.

**기술·채널 제약** — 스택 자율 선택. 초기 카카오톡 인앱 형태로 출발했으나 프로젝트 특성상 Capacitor 앱으로 우회.

**리스크 허용도** — 학습용. 평가·시연 강제 없음 → 실험적 결정의 자유도 높음.

**AI 활용 환경** — 팀 합의·제한 없음, 본인만 적극 활용, 외부 노출 자유.

## Problem

**사용자 문제 — 결정 피로(decision fatigue)** — 모임 장소 선정 시 사용자는 정보 부족이 아닌 **선택지 과잉**으로 결정하지 못함. 의견이 갈리고, 인원수에 맞는 장소를 못 찾고, 지도·리뷰·예약 앱을 오가며 피로가 쌓이고, 결정이 늦어짐. 기존 서비스가 검색에 집중했다면 본 서비스는 **결정 피로 감소**에 집중.

**본인 학습 문제 — "나만의 AI 활용 플로우 부재"** — 본인이 직접 명시한 빈틈: *"이 프로젝트를 안 했다면 AI를 단순 웹에서 사용하며 코드를 복사·붙여넣는 방식으로만 다뤘을 것."* 단순 도구 사용을 넘어선 **워크플로우 내재화**가 본인의 진짜 Problem.

**안 했으면 발생할 비용** — SSAFY 후 취업 포트폴리오 공백 + 첫 앱 출시 경험 부재 + AI 자동화 도구(MCP·서브에이전트·이슈 동기화 등)에 대한 체득 부재.

## Analyze

검토한 핵심 결정은 **2개**. 전체 압축 모드로 핵심만 서술.

### D1. 출시 채널 — 카카오톡 인앱 → Capacitor 하이브리드 앱 우회

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| (a) 카카오톡 인앱(공유 링크) | 설치 마찰 0, 즉시 진입 | 인앱 브라우저의 백그라운드 정책 → Group 플로우 Realtime WebSocket 끊김 위험, sessionStorage 휘발 가능, 앱 출시 학습 목표 미충족 | **기각** |
| (c) Capacitor 하이브리드 | 기존 Next.js 웹앱 그대로 재사용 → 시간 압축, 신기술 사용 경험, AI 친화도, **Play Store 출시 학습 목표 충족** | AAB 빌드·서명 학습 부담 (Google Play 앱 서명 B 시나리오 학습 필요) | **채택** |

**핵심 판단** — Phase 1의 시간·실력 제약 하에서 "이미 만든 웹앱을 재사용하면서 앱 출시 학습을 동시에 얻는 두 마리 토끼". 학습용 리스크 허용도가 높아 심사 실패 비용을 감수 가능했음. (RN/Flutter/네이티브는 검토 단계 진입 전 기각 — 시간 제약상 학습 곡선 부담이 결정적)

### D2. AI 활용 방식 — 단순 도구 → 자체 워크플로우 + MCP 통합 + Linear 자동화

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| (a) ChatGPT/Claude 웹에서 단순 복붙 | 진입 비용 0 | 컨텍스트 단절, 산출물 일관성 부재, 코드 흐름 미이해 | **기각** (이전 방식) |
| (b) Claude Code CLI 단순 사용 | IDE 통합 | 워크플로우 표준 부재, 팀원 가시성 0 | **부분 — 출발점** |
| (c) 자체 dev 파이프라인 + MCP 통합 (`CLAUDE.md` + dev-orchestrator + sub-agent + Google Play MCP) | 매 작업 산출물 자동 기록 → 유지보수 효율, AI 산출물 일관성, 배포 자동화 | 단기 개발 속도 양보, 학습 비용 | **채택 (v1.0까지)** |
| (d) (c) + Linear 자동 동기화 | 팀원 가시성 추가, 본인-팀원의 AI가 Linear 매개로 연결 | 도구 추가 학습 부담 | **채택 (v1.1부터)** |

**단계적 진화** — 처음부터 Linear까지 도입한 게 아님. **v1.0 출시까지 1개월(3/16~4/16)은 1인 자체 플로우만으로 운영** (CLAUDE.md, dev-orchestrator, sub-agent, Google Play MCP). v1.0 출시 후 v1.1 고도화 시점부터 Linear를 추가 도입해 협업 본격화.

**Linear 도입의 메타 결정** — 통념상 2인 팀에서 Linear 도입은 효과 대비 관리비용이 더 큰 도구. 그러나 **AI 자동화로 관리비용을 0에 수렴시키면 2인 팀에서도 ROI 회수 가능**하다는 가설로 도입. 추가 효과로 팀원도 Linear를 그대로 읽고 자신의 AI에 입력 → 프롬프트 시간 단축 → **본인의 AI ↔ 팀원의 AI가 Linear를 매개로 연결되는 협업 시스템** 구축. AI Quiz의 팀원 이탈 학습이 직접 트리거.

**검토 시점** — 특정 사고가 트리거가 아니라 **how_many 시작과 동시에 Claude Code 학습과 자체 플로우 구축을 병행**한 의도적 학습 곡선.

## Learnings

### 지금 다시 한다면

- **요구사항 정의·기획을 더 구체적으로** — 맛집 탐색(Food) 플로우는 사용자 요청 후 추가된 기능. 미리 사용자 입장에서 고려했다면 초기 설계에 포함됐을 것
- **공통 개발 플로우가 아닌 프로젝트별 적합 플로우** — 본 프로젝트에서 구축한 자체 플로우를 그대로 재사용하지 말고, **프로젝트 상황·요구사항에 맞춰 별도 구축**해야 함
- **사전 자동화 항목을 미리 정의** — Linear 자동 동기화·Google Play MCP 같은 자동화를 시작 시점에 정의했다면 추가 시간 단축 가능했음 (이번엔 진행 중간에 도입, Linear는 v1.0 출시 후에야 도입)
- **사전 가설·측정 지표를 계획 단계에서 고려** — 1개월 출시 압박과 첫 바이브 코딩 학습이 동시에 작용해 측정 의식이 후순위로 밀렸음. 다음엔 plan.md 작성 시점에 *"어떤 지표가 어떻게 개선될 것인지"* 가설부터 명시해야 사후 검증과 회고가 가능. 우연히 누적된 산출물에 의존하지 않고 *기획된 측정*으로 전환
- **사용자 기대 검증을 1차 구현 전** — HM-21 롤백 사례의 직접 교훈

### 당시엔 몰랐지만 지금 보이는 것

- 자동화 항목을 사전 정의하지 않은 비용이 **HM-21 같은 작업마다 누적**됨을 늦게 인지
- "공통 플로우"가 만능이 아니라는 것 — 프로젝트마다 제약·요구가 다르므로 매번 재단해야 함
- Linear는 더 일찍 도입했어도 됐을 가능성 — v1.0 1개월간 1인 자체 플로우만 고집한 건 협업 가시성을 그만큼 늦게 확보한 비용

### 다른 상황에 이식 가능한 원리

1. **AI 자동화로 통념적 ROI 한계 극복** — "2인 팀의 Linear는 관리비용이 효과를 초과한다"는 통념을, AI 자동화로 관리비용을 0에 수렴시켜 회수. 다음 프로젝트에서도 *"이 도구의 통념적 한계는 무엇이고, AI 자동화로 어디까지 끌어내릴 수 있는가"* 를 먼저 확인.

2. **단기 속도 양보 → 후반 효율 회수** — 자체 플로우 구축은 단기 속도 ↓이지만 매 작업의 산출물(plan.md·fix/·study-save)이 누적되어 **테스트·오류 수정·유지보수 단계에서 효율을 회수**. *방향성과 기록을 우선하고 속도는 누적 효율로 환산*.

3. **AI를 도구가 아닌 워크플로우로 내재화** — 단순 코드 생성기로 쓰지 않고, dev-orchestrator·sub-agent·MCP·Linear sync로 **개발 라이프사이클 전체에 통합**. 개인 산출물뿐 아니라 **팀원의 AI까지 워크플로우에 연결**되는 협업 시스템으로 확장 가능.

### 남은 한계 / 기술 부채

- **측정 인프라 부재** — Play Store 다운로드·MAU·결과 저장 건수·카톡 공유 클릭률 등 실사용 데이터 0. v1.1 안정화 단계에서 보강 예정
- **코드 흐름 100% 이해 미달** — 첫 바이브 코딩의 한계. AI 출력에 대한 검수 능력은 점진 보강 중
- **테스트 케이스 설계 부족** — 특히 **디자인 요소 회귀**가 반복 발생 (`.claude/fix/` 8건 중 일부). E2E 테스트 자동화·viewport 검증 도입 필요

### 보완 조치 — 워크플로우 룰 신설 (2026-04-25)

위 3개 한계를 다음 프로젝트에서 재발하지 않도록 **plan.md 작성 단계에서 강제**하는 룰을 전역 개발 규칙(`~/.claude/templates/dev-claude.md`)에 신설. CLAUDE.local.md ↔ dev-claude.md 심링크 구조를 통해 본 프로젝트 + 모든 신규 프로젝트에 자동 전파.

**검수 가능 수준 재정의** — "100% 이해"는 비현실적 목표라 폐기. 대신 **(1) 의도 설명 가능 (2) 잠재 버그 식별 가능 (3) 변형 영향 예측 가능** 3개를 모두 만족하는 "검수 가능 수준"으로 기준을 재설정. AI 출력의 미세 결함을 잡을 수 있는 최소 임계점만 강제.

**표준 템플릿 신설** — `~/.claude/templates/plan-template.md`에 위 3개 섹션을 ⭐ 표시로 포함, 신규 작업이 자동으로 가설·테스트·사전 학습을 의식하도록 구조화. 작업 크기에 따라 면제 escape clause 제공 (단순 작업은 한 줄 명시로 통과).

**작성 자체의 의미** — 본 룰들은 "측정·검수·테스트가 부재했다"는 회고를 **"다음에 같은 부재가 발생하지 않게 룰을 코드화했다"**로 닫는 메타 회수. 한계를 인지로만 끝내지 않고 시스템 변경으로 영구 봉합.
